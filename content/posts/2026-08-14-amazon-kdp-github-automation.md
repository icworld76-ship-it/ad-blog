생성형 AI 기술이 빠르게 발전하면서 아마존 KDP 전자책과 컬러링북 제작 장벽은 크게 낮아졌습니다.

예전에는 디자인, 편집, 표지 제작, 내지 구성까지 여러 사람의 손을 거쳐야 했지만 지금은 생성형 AI와 자동화 도구를 활용하면 1인 출판자도 비교적 빠르게 한 권의 책을 완성할 수 있습니다.

문제는 책 한 권을 만드는 순간보다 두 권, 세 권, 열 권으로 프로젝트가 늘어나기 시작한 뒤부터 발생합니다.

어느 파일이 최종본인지 헷갈리고, 표지 원본이 어디 있는지 찾지 못하고, KDP 등록 당시 어떤 키워드와 설명을 사용했는지 기억이 나지 않는 경우가 생깁니다.

특히 KDP 심사에서 수정 요청을 받았을 때 이전 파일과 수정 파일이 뒤섞이면 관리 난도가 급격히 올라갑니다.

지난 포스팅에서 소개한 아마존 KDP AI 고양이 컬러링북 제작부터 아마존 출판까지 완전 가이드에 이어 이번 글에서는 한 단계 더 나아가 KDP 프로젝트 자체를 하나의 시스템으로 관리하는 방법을 정리합니다.

핵심은 깃허브 저장소를 이용해 32페이지 원고, 표지, AI 생성 이미지, 프롬프트, 메타데이터, 수정 이력을 하나의 프로젝트 단위로 관리하는 것입니다.

깃허브를 단순히 개발자용 코드 저장소로만 생각할 필요는 없습니다.

파일의 변경 기록을 남기고 이전 버전으로 되돌릴 수 있다는 점만으로도 1인 출판자에게 상당히 유용한 작업 관리 도구가 될 수 있습니다.

1. 왜 KDP 전자책 출판에 깃허브 저장소 관리가 필요한가?

아마존 KDP 출판은 한 번 파일을 올리고 끝나는 작업이 아닙니다.

출판 전에는 원고 수정이 반복되고, 출판 이후에도 오탈자 수정, 표지 교체, 설명문 변경, 키워드 변경, 카테고리 조정이 발생할 수 있습니다.

KDP 심사 과정에서 내지 크기나 여백, 표지 규격 등의 문제로 파일을 다시 만들어야 하는 경우도 있습니다.

이 과정을 일반 컴퓨터 폴더에서만 관리하다 보면 흔히 다음과 같은 파일명이 등장합니다.

final.pdf

final2.pdf

final_real.pdf

final_real_last.pdf

final_really_last.pdf

이렇게 되기 시작하면 어떤 파일이 실제 KDP에 업로드된 버전인지 알기 어려워집니다.

깃허브에서는 파일이 변경될 때마다 기록을 남길 수 있기 때문에 어느 시점에 무엇을 수정했는지 확인하기가 쉽습니다.

예를 들어 표지 제목을 수정했다면 해당 수정 내용을 기록하고, 내지 14페이지 그림을 교체했다면 그 작업 역시 별도 변경 이력으로 남길 수 있습니다.

프로젝트가 많아질수록 이런 관리 방식의 차이는 매우 커집니다.

특히 AI로 이미지를 생성하는 경우에는 최종 이미지뿐 아니라 어떤 프롬프트를 사용했는지도 함께 저장하는 것이 좋습니다.

나중에 비슷한 시리즈를 제작할 때 기존 프롬프트를 다시 사용할 수 있고, 특정 그림체를 재현할 때도 큰 도움이 됩니다.

2. KDP 전자책 전용 깃허브 저장소 표준 구조

KDP 프로젝트를 관리할 때 가장 중요한 것은 처음부터 폴더 구조를 정해두는 것입니다.

책마다 다른 방식으로 파일을 저장하면 결국 다시 혼란이 생깁니다.

예를 들어 하나의 KDP 프로젝트 저장소를 다음과 같이 구성할 수 있습니다.

01_manuscript

02_cover

03_assets

04_metadata

05_export

06_tools

각 폴더의 역할을 명확하게 구분하는 것이 핵심입니다.

01_manuscript 폴더에는 책의 본문 원고와 내지 파일을 저장합니다.

32페이지 컬러링북이라면 1페이지부터 32페이지까지 번호를 붙여 관리하는 것이 좋습니다.

예를 들면 다음과 같습니다.

page-01.png

page-02.png

page-03.png

page-04.png

이 방식으로 32페이지까지 이어지면 누락된 페이지를 빠르게 확인할 수 있습니다.

02_cover 폴더에는 전면 표지 원본과 KDP 업로드용 펼침 표지를 저장합니다.

표지 역시 원본과 최종 업로드 파일을 구분하는 것이 좋습니다.

03_assets 폴더에는 AI 생성 이미지 원본, 참고 이미지, 편집 전 파일 등을 저장합니다.

AI 이미지 생성에 사용한 프롬프트도 TXT 또는 MD 파일 형태로 함께 보관하면 좋습니다.

04_metadata 폴더에는 KDP 등록에 필요한 정보를 저장합니다.

여기에는 책 제목, 부제목, 저자명, 도서 설명, 검색 키워드, 카테고리, 가격 정보 등을 기록합니다.

05_export 폴더에는 실제 KDP에 업로드하는 최종 PDF 파일을 저장합니다.

06_tools 폴더에는 PDF 생성이나 이미지 크기 확인, 페이지 수 검증 등에 사용하는 자동화 스크립트를 보관할 수 있습니다.

이렇게 구조를 고정해두면 다음 책을 만들 때도 같은 저장소 구조를 복사해서 사용할 수 있습니다.

3. 32페이지 PDF 원고 및 표지 에셋 관리 실전 3단계

첫 번째 단계는 원본과 최종 파일을 구분하는 것입니다.

AI 이미지 생성 직후의 파일과 실제 KDP 업로드에 사용하는 파일은 반드시 분리하는 것이 좋습니다.

예를 들어 AI가 생성한 원본 이미지는 assets 폴더에 저장하고, 크기 조정과 편집이 끝난 최종 내지 이미지만 manuscript 폴더에 넣는 방식입니다.

두 번째 단계는 메타데이터를 별도로 관리하는 것입니다.

많은 사람들이 KDP 등록 화면에 제목과 설명을 입력한 뒤 별도로 기록하지 않습니다.

하지만 시간이 지나면 어떤 키워드를 사용했는지 기억하기 어렵습니다.

따라서 metadata.md 파일 하나를 만들어 다음 내용을 정리해두는 것이 좋습니다.

도서 제목

부제목

저자명

도서 설명

검색 키워드

카테고리

책 크기

페이지 수

출판일

가격

이렇게 기록해두면 이후 다른 책을 제작할 때 참고하기도 쉽습니다.

세 번째 단계는 버전을 구분하는 것입니다.

버전을 복잡하게 관리할 필요는 없습니다.

예를 들어 다음 정도만 구분해도 충분합니다.

v0.1 초안 제작 단계

v0.5 내지 및 표지 완성 단계

v1.0 KDP 최초 업로드 단계

v1.1 오탈자 또는 이미지 수정 단계

v2.0 개정판 단계

중요한 것은 버전 번호보다 어떤 상태의 파일인지 명확하게 알아볼 수 있게 만드는 것입니다.

4. KDP PDF 자동 검증 시스템 구축

KDP 출판 과정에서 반복적으로 확인해야 하는 항목들이 있습니다.

대표적인 것이 페이지 수, 이미지 크기, 내지 규격, 표지 크기입니다.

이런 부분은 사람이 매번 직접 확인할 수도 있지만 프로젝트가 늘어나면 자동 검증이 훨씬 효율적입니다.

예를 들어 자동 검증 과정에서 다음 항목을 확인하도록 구성할 수 있습니다.

내지 이미지가 정확히 32장인지 확인

각 이미지의 가로 세로 크기가 동일한지 확인

PDF 페이지 수가 32페이지인지 확인

필수 파일이 모두 존재하는지 확인

표지 파일이 지정된 폴더에 있는지 확인

최종 PDF 파일이 정상 생성되었는지 확인

여기에 GitHub Actions를 연결하면 파일이 변경될 때마다 자동으로 검증 작업을 실행하도록 만들 수도 있습니다.

작업자가 새로운 내지 이미지를 업로드하면 자동으로 페이지 수와 파일명을 확인하고 문제가 있으면 오류를 표시하도록 하는 방식입니다.

조금 더 발전시키면 이미지 크기 검사, PDF 생성, 결과 파일 저장까지 자동화할 수 있습니다.

다만 여기서 한 가지 주의할 점이 있습니다.

이미지 파일에 표시된 DPI 정보만으로 인쇄 품질을 판단해서는 안 됩니다.

실제 인쇄 품질은 이미지 픽셀 크기와 최종 인쇄 크기의 관계가 더 중요합니다.

따라서 단순히 300DPI라는 숫자만 검사하기보다는 실제 KDP 내지 규격에 맞는 충분한 픽셀 크기를 확보했는지 확인하는 방식이 더 안전합니다.

5. 대용량 이미지와 PDF는 어떻게 관리할까?

깃허브는 매우 편리하지만 고해상도 PNG와 PDF처럼 파일 용량이 큰 자료를 무제한으로 저장하는 용도로 만들어진 서비스는 아닙니다.

특히 수십 장의 고해상도 이미지를 계속 저장하면 저장소 크기가 빠르게 커질 수 있습니다.

이런 경우 Git LFS를 활용할 수 있습니다.

Git LFS는 대용량 파일을 일반 Git 파일과 다르게 관리하는 방식입니다.

PNG, PSD, PDF 같은 대용량 파일을 LFS 대상으로 설정하면 저장소 관리가 조금 더 편리해집니다.

하지만 Git LFS 역시 사용량 제한과 비용 정책이 존재할 수 있기 때문에 무조건 모든 원본 파일을 올리는 방식보다는 필요한 파일만 선별해서 관리하는 것이 좋습니다.

예를 들어 AI 생성 과정에서 나온 실패 이미지까지 전부 저장할 필요는 없습니다.

최종 후보 이미지와 실제 사용된 원본만 남기는 방식이 효율적입니다.

KDP 제작 과정을 시스템화하면 전체 흐름을 다음과 같이 만들 수 있습니다.

AI 이미지 생성

자동 검증 실행

KDP 업로드용 최종 파일 생성

이 구조가 안정적으로 잡히면 새로운 책을 만들 때마다 처음부터 모든 과정을 다시 고민할 필요가 없습니다.

기존 저장소를 복사한 뒤 이미지와 메타데이터만 교체하면 새로운 출판 프로젝트를 빠르게 시작할 수 있습니다.

여기에 생성형 AI까지 연결하면 작업 효율은 더욱 높아집니다.

예를 들어 책의 주제와 캐릭터 콘셉트를 정한 뒤 32개의 장면 프롬프트를 생성하고, 각 이미지 파일명을 자동으로 정리하고, 메타데이터 초안까지 자동 생성하는 흐름도 만들 수 있습니다.

결국 목표는 한 권의 책을 만드는 것이 아니라 반복 가능한 출판 시스템을 만드는 것입니다.

7. 블로그 유입과 애드센스 수익화까지 연결하는 방법

KDP 프로젝트를 깃허브로 관리하면 단순히 출판 작업만 편해지는 것이 아닙니다.

이 과정을 블로그 콘텐츠로 활용할 수도 있습니다.

예를 들어 실제로 사용하고 있는 저장소 구조를 공개하고 KDP 제작용 폴더 템플릿을 공유할 수 있습니다.

독자 입장에서는 단순한 이론 글보다 실제 사용할 수 있는 자료가 있는 글에 더 오래 머물 가능성이 높습니다.

KDP 출판 과정에서 발생하는 문제 역시 좋은 콘텐츠가 됩니다.

예를 들어 다음과 같은 주제로 계속 확장할 수 있습니다.

KDP 표지 크기 오류 해결법

컬러링북 내지 여백 설정법

AI 이미지로 KDP 출판할 때 주의할 점

KDP 심사 반려 후 재업로드 방법

32페이지 컬러링북 자동 PDF 제작법

GitHub Actions를 활용한 PDF 자동 검증법

이런 글을 시리즈로 연결하면 하나의 글을 읽고 다른 관련 글로 이동하는 내부 구조를 만들 수 있습니다.

결국 KDP 출판 경험 자체가 또 하나의 블로그 콘텐츠 자산이 되는 셈입니다.

결론

아마존 KDP 출판에서 중요한 것은 책 한 권을 빠르게 만드는 것만이 아닙니다.

프로젝트가 계속 늘어나도 혼란 없이 관리할 수 있는 구조를 만드는 것이 훨씬 중요합니다.

깃허브 저장소를 활용하면 32페이지 내지, 표지, AI 생성 이미지, 프롬프트, 메타데이터, 최종 PDF 파일을 하나의 프로젝트 안에서 체계적으로 관리할 수 있습니다.

여기에 버전 관리와 자동 검증까지 추가하면 KDP 출판 작업은 단순 반복 작업에서 하나의 자동화 파이프라인으로 발전합니다.

한 권을 만들 때는 이런 시스템이 다소 번거롭게 느껴질 수 있습니다.

하지만 다섯 권, 열 권, 수십 권으로 늘어나는 순간 관리 시스템의 차이가 생산성 차이로 이어집니다.

KDP를 단발성 부업이 아니라 지속적인 디지털 출판 사업으로 운영할 생각이라면 처음부터 저장소 구조와 버전 관리 방식을 만들어두는 것이 좋습니다.
